# Llama→Qwen old-method reproduction under native lm-eval

Independent MCQ (OpenBookQA / ARC-Challenge) and GSM8K pipelines. Full28 MLP + diagonal head matrices + rank64 receiver-space residual are copied unchanged from the frozen framework. Each group independently trains Stage A for2epochs and Stage B for4epochs. MCQ candidate-distribution KL and GSM8K Hybrid are the old objectives; this is NOT the later shared-adapter experiment.

Task prompt, candidate texts, demonstration formatting, generation stops, token budgets, filters and aggregation come from installed lm_eval0.4.12. Local dataset routing replaces download locations only. Native paths use HFLM; oracle injection must first reproduce HFLM continuation likelihoods and16-token greedy generation in smoke checks. No chat template is applied. No private flexible parser exists here.

Only model-side context KV provenance changes. For each original harness context, native token0 remains and the final context token is processed natively as the readout. The intervening tokens are translated with original Full-Sync copy/drop and retain target positions. Multiple-choice continuation log-likelihood uses harness token boundaries and full candidate text. Generation is inherited from HFLM, including stopping and postprocessing.

Training splits: OBQA1024 officialtrain, ARC1024 officialtrain, GSM2048 officialtrain; validation128 each, GSM withheld fromtrain. GSM training/internal-validation demonstrations are drawn only from training subset (no validation answers). Benchmark uses the official fulltrain demonstration pool and fixed seed1234. MMLU-Pro/HellaSwag are evaluation-only. No old checkpoint is reused.

Core evaluation uses first128 official evaluation examples per task, clearly labeled a feasibility pilot. OOD MMLU uses128 total examples allocated across14 subjects; HellaSwag128. Never call these full published benchmark scores. Official `acc`, `acc_norm`, GSM strict/flexible exact match, and MMLU CoT exact match are retained. Selection uses validation loss only.

`pipeline_status.json` tracks phase. Stages resume from full epoch state (`last.pt`, optimizer and scaler); smoke and real runs are isolated. `RESULTS.md` is generated by the pipeline. Training and evaluation outputs are retained separately.
